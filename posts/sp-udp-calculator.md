# 무엇을 만들었나

시스템프로그래밍 수업 실습으로, 클라이언트가 두 정수와 연산자를 보내면 서버가 계산해서 돌려주는 UDP 계산기를 만들었습니다. 서버는 클라이언트마다 지금까지의 결과 중 최솟값과 최댓값을 따로 기억합니다.

- 서버: `cal_udp_server.c`, 클라이언트: `cal_udp_client.c`
- 연산자 `$`를 보내면 그 클라이언트의 기록을 지웁니다.
- 디버그 출력은 `#if DEBUG`로 감싸고, `gcc -o 실행파일 소스.c -DDEBUG`처럼 옵션을 맨 뒤에 붙여서 켭니다.

---

# 설계: 한 소켓으로 여러 클라이언트를 구분하기

UDP는 연결이 없어서 소켓 하나로 모든 클라이언트의 패킷을 받습니다. 누가 보냈는지는 `recvfrom()`이 채워 주는 `sockaddr_in`(주소와 포트)으로 구분합니다. 그래서 클라이언트 정보를 담는 구조체 배열을 따로 두었습니다.

```c
struct cal_client {
    struct sockaddr_in cliaddr;   // 누구인지
    int min;                      // 이 클라이언트의 최솟값
    int max;                      // 이 클라이언트의 최댓값
};
struct cal_client clients[MAX_CLIENTS];
```

`recvfrom()`으로 받을 때마다 보낸 쪽의 주소를 배열에서 찾고, 없으면 빈 칸에 새로 등록합니다.

# 겪은 문제: 서버가 응답을 받지 못했다

원인은 서버에서 `bind()`를 빠뜨린 것이었습니다. 클라이언트는 서버의 3800번 포트로 보내는데, 서버 소켓이 그 포트에 묶여 있지 않으면 패킷이 서버 소켓에 도착하지 않습니다.

```c
addr.sin_port = htons(PORT_NUM);
if (bind(sockfd, (struct sockaddr *)&addr, sizeof(addr)) == -1)
    return 1;      // 이 호출이 있어야 서버가 3800번 포트를 차지한다
```

UDP에는 `connect()`와 `accept()` 과정이 없어서, 포트를 잡는 일을 `bind()`가 전담한다는 점을 처음 실감했습니다. 클라이언트는 `bind()`를 생략해도 운영체제가 임시 포트를 붙여 주지만, 서버는 클라이언트가 찾아올 고정 포트가 필요합니다.

# 다시 읽다가 발견한 문제

이 글을 쓰려고 제출한 코드를 다시 읽다가 몇 가지를 발견했습니다. 제출 당시 실행 결과는 맞았지만 코드는 고칠 점이 있습니다.

- 클라이언트를 찾는 `memcmp(..., sizeof(cliaddr))`에서 `cliaddr`가 포인터라 포인터 크기(8바이트)만 비교합니다. 우연히 `sockaddr_in`의 앞 8바이트가 주소 종류, 포트, IP라서 동작은 하지만, 구조체 전체 크기(`sizeof(struct sockaddr_in)`)로 써야 맞습니다.
- 클라이언트 등록 때 `max`를 `-1`로 초기화해서, 결과가 모두 `-1`보다 작으면 최댓값이 틀리게 나옵니다. `INT_MIN`으로 초기화해야 합니다. 뒤에 만든 TCP 버전에서는 `INT_MIN`을 썼습니다.
- UDP는 패킷이 유실되거나 순서가 바뀔 수 있는데, 이 프로그램은 재전송이나 응답 확인을 하지 않습니다.

# 배운 점

- UDP 서버는 `socket → bind → recvfrom/sendto`, 클라이언트는 `socket → sendto/recvfrom`이다.
- 연결이 없으니 클라이언트의 상태는 서버가 주소를 키로 직접 관리해야 한다.
- 구조체를 네트워크로 보낼 때는 `htonl`, `ntohl`로 정수의 바이트 순서를 맞춘다.
- 같은 이름의 변수라도 포인터인지 구조체인지에 따라 `sizeof` 결과가 달라진다.
