# CSRF란

CSRF(Cross-Site Request Forgery)는 로그인한 사용자의 브라우저가 자기도 모르게 공격자가 만든 요청을 보내게 하는 공격입니다. 브라우저는 같은 사이트로 가는 요청에 쿠키를 자동으로 붙여서 보내는데, 서버가 "이 요청이 정말 사용자가 의도한 것인가"를 따로 확인하지 않으면 공격이 통합니다.

---

# 실습에서 본 두 가지 형태

워게임 사이트의 1:1 문의 게시판을 이용한 실습이었습니다. 관리자가 문의글을 열어 보면, 글 안에 심어 둔 요청이 관리자의 권한으로 실행되는 구조입니다.

- GET 방식: 권한을 바꾸는 기능이 `GET` 요청이면, 게시글에 `<img>` 태그를 넣는 것만으로 충분합니다. 이미지를 불러오는 것처럼 보이지만 브라우저는 그 주소로 요청을 보냅니다.
- POST 방식: `POST`는 주소만 넣어서는 안 되고, 숨겨진 `<form>`을 만들어 자동으로 제출하는 스크립트가 필요합니다.

그리고 두 문제는 서버 포트가 달랐습니다. 요청 방식과 대상 주소를 개발자 도구나 프록시로 직접 확인하고 나서 공격 코드를 작성해야 했습니다.

---

# 왜 통하는가

- 상태를 바꾸는 기능을 `GET`으로 만들어 두면, 링크나 이미지 한 줄로 실행됩니다.
- 쿠키는 요청을 누가 만들었는지와 상관없이 붙습니다.
- 서버가 요청의 출처나 토큰을 검증하지 않습니다.

---

# 막는 방법

- CSRF 토큰: 폼마다 서버가 만든 일회성 값을 넣고, 요청이 올 때 검증합니다.
- `SameSite` 쿠키 속성: 다른 사이트에서 시작된 요청에는 쿠키를 붙이지 않게 합니다.
- `Origin` 또는 `Referer` 헤더 검증
- 상태를 바꾸는 기능은 `GET`이 아니라 `POST` 등으로 만들기. 다만 `POST`라고 해서 안전한 것은 아니고, 위의 토큰 검증이 함께 필요합니다.

> 이 글은 허가된 실습 환경에서 배운 내용을 개념 위주로 정리한 것입니다. 실제 서비스에 시도하면 안 됩니다.
