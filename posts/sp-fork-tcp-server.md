# 무엇을 만들었나

앞서 만든 UDP 계산기를 TCP로 바꾸고, 클라이언트가 접속할 때마다 `fork()`로 자식 프로세스를 만들어 그 클라이언트만 전담하게 했습니다. 여러 클라이언트가 동시에 접속해도 서로 영향을 주지 않습니다.

- 입력 형식은 `숫자1 숫자2 연산자`입니다.
- 서버 화면에 `CLIENT #N Connect`, `FROM CLIENT #N`, `Disconnected` 같은 줄이 나옵니다.
- 클라이언트가 `0 0 $`를 보내면 연결을 끝냅니다.

---

# 구조: 부모는 접속만, 자식은 계산만

```c
while (1) {
    client_fd = accept(listen_fd, ...);
    client_num++;                     // 부모가 번호를 매긴다
    pid = fork();
    if (pid == 0) {                   // 자식
        close(listen_fd);             // 접속 받는 소켓은 자식에게 필요 없다
        /* client_fd로 읽고, 계산하고, 쓰는 반복 */
        return 0;
    } else {                          // 부모
        close(client_fd);             // 연결된 소켓은 자식이 담당한다
    }
}
```

- `fork()` 직후에는 부모와 자식이 같은 소켓 디스크립터를 모두 갖고 있어서, 각자 필요 없는 쪽을 닫습니다.
- 최솟값과 최댓값은 자식 프로세스 안의 변수라서 클라이언트마다 따로 유지됩니다. UDP 버전에서는 주소를 키로 하는 배열이 필요했는데, 프로세스가 나뉘면서 그 배열이 필요 없어졌습니다.
- `signal(SIGCHLD, SIG_IGN)`을 설정해서 끝난 자식이 좀비 프로세스로 남지 않게 했습니다.

# 실행 확인

서버와 클라이언트 여러 대를 띄우고 `ps -ef`로 서버 프로세스 아래에 자식이 클라이언트 수만큼 생기는지, `netstat -atp`로 연결 상태가 어떤지 확인했습니다. 보고서에도 이 두 화면을 캡처로 넣었습니다.

---

# 다시 읽다가 발견한 한계

- TCP는 바이트 스트림이라서 `read()`가 구조체 크기만큼 한 번에 돌려준다는 보장이 없습니다. 이 코드는 `read`가 구조체 크기와 다르면 연결이 끝난 것으로 보는데, 실제로는 모자란 만큼 반복해서 읽어야 안전합니다. 짧은 데이터를 로컬에서 주고받는 실습에서는 잘 동작했습니다.
- 구조체를 `write`로 그대로 보내므로 서버와 클라이언트의 구조체 배치(패딩)가 같다는 전제가 필요합니다. 두 프로그램을 같은 환경에서 컴파일하는 실습이라 문제가 없었습니다.
- `accept()`에서 오류가 나면 서버 반복문이 끝납니다.

---

# 배운 점

- 접속을 받는 소켓(`listen_fd`)과 연결된 소켓(`client_fd`)은 다른 것이다.
- `fork()` 뒤에는 부모와 자식이 각자 쓰지 않는 디스크립터를 닫아야 한다.
- 프로세스를 나누면 상태 공유가 어려워지는 대신, 클라이언트별 상태를 따로 관리할 필요가 없어진다.
- `SIGCHLD`를 무시하면 좀비를 막을 수 있다. 다만 이 설정은 `exec`로 실행한 프로그램에도 이어지므로, 자식을 `wait`해야 하는 프로그램에서는 주의해야 한다.
